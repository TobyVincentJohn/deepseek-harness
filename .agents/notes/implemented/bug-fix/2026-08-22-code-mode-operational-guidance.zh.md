# Agent Note: Code Mode 操作指南与碎片化运行提醒

Status: implemented

[English](2026-08-22-code-mode-operational-guidance.md) | 中文

## 问题

Code Mode SDK 虽然要求模型批处理确定性工作，但遗漏了决定批处理能否成功的操作事实。模型可能依赖 `require`、把 worker 进程目录误认为会话工作区、遗漏嵌套工具的必填参数、在只读任务中创建中间文件，或把一次归档分析拆成许多不同的 `run_code` 程序。精确参数重复 guard 无法识别最后一种模式，因为每段程序文本都不同，而且外层调用之间还会出现嵌套分发。真实归档回放还暴露了三个具体歧义：模型把 `glob` 等 SDK 名称作为顶层调用发出、猜测多种 Bash 返回结构，并在命令以非零状态退出时仍把已经 resolve 的 Bash 调用当成成功。

## 决策

TypeScript SDK 与 `run_code` schema 要求模型通过已声明的工具绑定完成任务 I/O，避免使用 Node 模块与 `process` API，通过嵌套工具解析相对工作区的路径，并传入嵌套工具的所有必填参数。Code Mode 专属段落区分唯一的顶层 `run_code` 传输与 SDK 方法名，并明确禁止模型把后者作为工具调用发出。两种语言的 SDK 都要求只读任务避开变更类工具和创建文件的命令。工作区检查遵循窄化顺序：`glob` 定位候选文件，`grep` 定位证据，`read` 只返回相关上下文窗口。随产品交付的 `readLimit` 为 200 行，因此显式的宽范围读取也无法绕过该上下文上限。归档、日志和数据集分析使用一个流式 Bash 流水线，计算带来源标识的有界汇总，不为每个文件或子问题分配外层程序，也不返回原始记录。

程序指南把声明的返回类型视为精确约定。前台 Bash 结果通过 `kind`、`exitCode`、`stdout.text` 与 `stderr.text` 消费；promise resolve 与命令成功彼此独立。Bash 命令会显式调用非 shell 解释器，多行脚本使用带引号的 heredoc。解析器会防御异构事件结构；某次运行失败后，只修复证据指向的最小成因并重试一次，而不是换用另一个兼容 wrapper。

Bash 的 `description` 字段是可选显示元数据，省略时确定性回退为 `Run shell command`；只有 `command` 仍是必填项。随附的 Web 与 headless bundle 在未设置 `DSH_TOOLS_MODE` 时默认使用 `both`，使普通会话同时公开 Codex 风格的原生发现／编辑工具，以及供有意进行确定性批处理的 `run_code`。操作方与专用 Code Mode preset 仍可显式选择 `native` 或 `code`。

`repeat-tool-reminder` 接受 `countByTool`，其中的通配工具名模式使匹配的根调用忽略参数、按工具名计数。嵌套分发对该根调用链透明；另一条受跟踪的根调用会重置它。这类序列收到不含参数的合并提醒，而 `countByTool` 之外的工具仍按规范参数精确匹配。包默认值为空，基础 bundle 配置为 `[run_code, bash]`：碎片化 wrapper 程序与不断变化的原生 shell 探测，是实际观察到的两类批量分析循环。

提醒仍只提供建议。它不会阻止调用，也不会施加通用运行次数上限；worker 运行时的进程目录与 Node 能力保持不变。

## 验证

工具生成测试固定 TypeScript 与 Python SDK 说明、按语言区分的 `run_code` 描述、Code Mode 顶层调用／SDK 方法区分、精确 Bash 结果处理、可选显示元数据、读取／搜索／Bash 选择指南、200 行读取上限以及 Bash 定义。Guard 测试会改变外层参数、在外层调用之间执行嵌套调用、覆盖两级提醒，并验证另一条受跟踪的根工具会重置序列。无密钥快照固定组装后的 Code Mode 提示词与传输 schema。真实 OpenRouter 归档运行会依据暂存数据集的新副本检查调用选择、工作区写入、完成状态、命令失败和答案证据。一次 Code Mode 回放消除了直接调用 SDK 名称的问题，但在已经取得决定性证据后仍超过 22 个分析步骤，证明仅靠建议性的合并提醒无法让该模型达到 Codex 风格的收敛，因此采用 `both` 默认值。

最终默认模式回放用时 187.586 秒：调用一次 `glob`、一次定向 `read` 与十四次原生 Bash，在 Bash 连续调用达到 3／5／8 次时收到提醒；turn 正常完成，暂存目录全部 66 个文件的 checksum 均未变化。可比的已完成 Code Mode 回放用时 446.903 秒，因此原生加批处理的呈现方式把墙钟时间降低了 58%。恢复前仍有三个模型生成的解析命令因 Python 错误退出；本次变更消除了协议与必填标签失败，但不会让模型编写的分析代码永不出错。

## 曾考虑的替代方案

**所有工具都忽略参数、只按名称计数。** 否决，因为针对不同目标的连续读取、搜索、编辑和轮询属于正常进展。忽略参数的计数需要显式的窄范围列表。

**把嵌套分发视为链重置。** 否决，因为每个有用的 Code Mode 程序都包含嵌套调用；该规则会使外层 `run_code` 序列在结构上不可见。

**达到固定程序数量后阻止调用。** 否决，因为探索性工作可能合理地需要多个程序，而且该 guard 的既定职责是提供建议。阈值提醒保留模型的决定权。

**在本次修复中改变 worker 的进程目录。** 暂缓，因为这会改变运行时语义而非模型指南，需要单独分析兼容性与隔离。嵌套工具已持有会话工作区解析约定。

## 后果

Code Mode 请求会携带额外的稳定提示词与 schema 文本。模型会在常见运行时错误和违反只读要求之前收到具体纠正；即使程序文本或嵌套工具发生变化，碎片化的 `run_code` 序列也会触发提醒。合理的长序列可能在配置阈值处收到提醒，但执行行为不变。`both` 默认值会同时发送原生 schema、SDK 与传输，从而增加固定请求前缀，换取更少的纯 wrapper 恢复轮次；更重视前缀大小而非工具易用性的部署仍可设置 `DSH_TOOLS_MODE=code`。

较小的读取上限以便捷的整文件读取换取可预测的上下文增长；调用方可在需要时分页读取目标源码窗口。搜索与 Bash 仍是建议选择，而不是按文件类型强制禁止，因此特殊任务仍可在上限内直接读取结构化文本。
